## 0. 先建立整体印象（架构一分钟速览）

在逐行读代码之前，先把整条链路在脑子里铺开，后面每段代码都能"对号入座"。

```
┌──────────────┐        ┌────────────────────┐        ┌───────────────────┐
│  DSH 桌面应用  │        │   bridge.js（Node） │        │  uni-app 客户端    │
│  (Node 服务)  │ ◄────► │   监听 0.0.0.0:3081 │ ◄────► │  H5 / Android App │
│  0.0.0.0:3080│        │   反向代理 + 换cookie│        │                   │
└──────────────┘        └────────────────────┘        └───────────────────┘
  白名单 Host/Origin 校验，会 403 拒绝未知来源
```

关键事实：

1. **DSH 是一个运行在局域网里的 Node 服务**，监听 `3080` 端口，提供两类接口：
   - **HTTP RPC**：`POST /api/{method}`，比如 `session/list`、`session/prompt`。
   - **WebSocket mux**：`/api/remote.mux`，一条物理连接上复用多条逻辑流（用于流式聊天）。
   - DSH 有 **Host / Origin 白名单**，直接从不被信任的来源请求会得到 `403 forbidden`。

2. **bridge.js**（项目根目录，`node bridge.js` 启动）是一个反向代理桥，监听 `3081`：
   - `GET /auth?token=xxx`：帮客户端换 cookie（它直连 DSH，用白名单里的 Host，把 DSH 返回的 `set-cookie` 抓出来，以 JSON 返回）。
   - `POST /api/*`：透明转发 HTTP 请求给 DSH（改 Host、剥掉 origin 等安全头、透传 Cookie）。
   - `WebSocket /api/remote.mux`：透明字节管道转发给 DSH。

3. **客户端是双端的**，两端的"接线方式"不同（这是本项目的核心设计点）：
   - **H5 端**：开发期走 Vite 的 dev proxy（`vite.config.ts` 里把 `/auth`、`/api` 转发到 DSH `3080`），浏览器同源，**cookie 由浏览器自动管理**，代码几乎不用管 cookie。
   - **App 端（Android）**：直连 bridge（默认 `http://192.168.8.219:3081`），**没有浏览器的自动 cookie 管理**，必须手动存 cookie、手动在请求头带 Cookie、还要额外写进系统 `CookieManager` 让原生 WebSocket 能带上。

4. 项目用 **Pinia** 做全局状态、**TypeScript** 写类型、**markdown-it + mp-html** 渲染 AI 的 Markdown 回复、**uni-ui 的 `uni-data-select`** 做下拉框。

下面进入正题。

# A 部分：项目用到的所有 uni-app 相关知识

## A.1 跨端条件编译 `#ifdef` / `#ifndef`

### 是什么

uni-app 是"一套代码多端运行"的框架。但不同端（H5、App、各小程序）能力差异很大，有些代码只能在某端写。**条件编译**就是用"注释"这种特殊写法，让编译器在打包时**只保留当前平台需要的代码，把其他平台的代码删掉**。

它本质上由 uni-app 的编译工具链在构建期处理：比如打包 H5 时，`#ifdef APP-PLUS` 里的代码会被整体移除；打包 App 时，`#ifdef H5` 里的代码被移除。

### 官方规定的语法

条件编译借助注释实现，有四种写法（对应 js / css / html）：

```js
// #ifdef 平台标识
// 只有该平台才会编译进来
// #endif

// #ifndef 平台标识
// 除了该平台之外都编译
// #endif
```

```css
/* #ifdef H5 */
/* H5 才生效的样式 */
/* #endif */
```

```html
<!-- #ifdef APP-PLUS -->
<!-- App 端才渲染的节点 -->
<!-- #endif -->
```

几个官方文档里的关键注意点：

- 条件编译**只对当前文件有效**，不能跨文件共享状态。
- `#ifdef` / `#ifndef` 必须**成对出现**，且必须独占一行（`// #ifdef` 后面不能跟代码）。
- 平台标识要用官方定义的值：本项目用到的两个是 **`APP-PLUS`**（5+ App，即 Android/iOS 原生 App）和 **`H5`**。其他常见还有 `MP-WEIXIN`（微信小程序）、`APP-PLUS` 大写写法实际不区分大小写等。
- `#ifdef` 里可以写 `||`、`&&` 组合，例如 `#ifdef H5 || APP-PLUS`。

### 项目里具体怎么用

这个项目**大量依赖条件编译来分叉双端实现**，最典型的三处：

**① 连接对象的实例化分叉**（`src/api/client.ts`）：

```ts
let connectFunction: BaseConnect;

// #ifdef H5
// H5：走 proxy（同源），uni.request 底层是 XHR，浏览器自动存 cookie
import { H5 } from './connect/H5';
connectFunction = new H5();
// #endif

// #ifdef APP-PLUS
import { AppConnect } from './connect/app';
connectFunction = new AppConnect();
// #endif
```

打包 H5 时，`import { H5 }` 和 `new H5()` 被保留，App 的那两行被删；打包 App 时相反。`connectFunction` 变量名两端共用，但指向的是**不同的类实例**。

**② App 端专属的 CookieManager 写入**（`src/api/connect/app.ts`）：

```ts
// #ifdef APP-PLUS
function setCookieToWebview(cookie: string): void {
  // plus.android 是 App 端专属能力，H5 没有 plus 对象，必须包在条件编译里
  // ...
}
// #endif
```

如果这段不包条件编译，H5 打包时 `plus` 未定义，运行会直接报错。

**③ WebSocket URL 的拼接分叉**（`src/api/ws.ts`）：

```ts
function wsUrl(): string {
  // #ifdef H5
  const proto = location.protocol === 'https:' ? 'wss:' : 'ws:';
  return `${proto}//${location.host}/api/remote.mux`;
  // #endif

  // #ifdef APP-PLUS
  const base = String(uni.getStorageSync(KEY_BASE_URL) || '');
  return base.replace(/^http/, 'ws') + '/api/remote.mux';
  // #endif

  // #ifndef H5 || APP-PLUS
  return '';
  // #endif
}
```

- H5 端：`location.host` 是浏览器当前地址，走同源 Vite proxy。
- App 端：从 storage 里读桥地址，把 `http` 换成 `ws` 拼出 WebSocket 地址。

> 小结：条件编译解决的是"同一份源码，编译出两套不同代码"的问题。读这种项目时，**看到 `#ifdef` 要先问"我现在在哪个端"**，把另一端的代码在脑子里划掉。

## A.2 `uni.request`（HTTP 请求）

### 是什么

`uni.request` 是 uni-app 封装的**跨端 HTTP 请求 API**。它把不同端的底层实现统一成一套参数：

- **App 端**：底层是 **`plus.net.XMLHttpRequest`**（5+ Runtime 的原生网络请求，不是 WebView 的 XHR）。
- **H5 端**：底层是**浏览器原生 `XMLHttpRequest`**。
- 小程序端：`wx.request`。

所以你在 uni-app 里写 `uni.request`，H5 打包出来运行时其实走的是浏览器 XHR，App 打包出来走的是原生网络。

### 官方文档的关键点

- **返回 Promise**：新版 uni-app 中 `uni.request` 支持 `await`，返回成功回调里的 `res` 对象；同时也支持传统 `success / fail / complete` 回调写法。
- **参数是 `header`（单数），不是 `headers`**：这是和 axios 最大的不同，写错就带不上请求头。
- **请求体参数叫 `data`**，不是 `body`。
- `res` 结构：`res.statusCode`（HTTP 状态码）、`res.data`（响应体）、`res.header`（响应头）。
- `method` 默认 `GET`，支持 `POST/PUT/DELETE` 等。
- 可配 `timeout`、`dataType`（返回数据格式，默认 json）、`responseType`（App/H5 支持 `arraybuffer` 等）。

### 项目里具体怎么用

**① 回调写法 + 手动包 Promise**（`src/api/connect/app.ts` 的 `connect()`）：

```ts
uni.request({
  url: `${baseUrl()}/auth?token=${encodeURIComponent(token)}`,
  method: 'GET',
  success(result) {
    const data = result.data as any;
    if (result.statusCode === 200 && data?.ok && data.cookie) {
      // ... 存 cookie
      resolve({ ok: true, message: '连接成功' });
    } else if (result.statusCode === 401 || data?.status === 401) {
      resolve({ ok: false, message: 'token 无效' });
    }
  },
  fail(e) {
    resolve({ ok: false, message: `桥连接失败：${e.errMsg}` });
  },
});
```

这里用回调是因为需要区分 `success`（请求发出且收到响应，但不一定是 200）和 `fail`（网络层失败、根本没连上）。

**② async/await 写法**（`src/api/connect/app.ts` 的 `send()`）：

```ts
const res = await uni.request({
  url: `${baseUrl()}/api/${method}`,
  method: 'POST',
  header,
  data: buildRequest(method, request),
});
return res.data;
```

`await` 等价于拿到了 success 回调的 `res`，所以 `res.statusCode`、`res.data` 直接用。

> 注意对比：H5 端（`src/api/connect/H5.ts`）用的是 `fetch`（浏览器原生），因为 H5 就是跑在浏览器里，直接 `fetch` 更顺手。App 端则必须用 `uni.request`（走原生网络）。这也是"同一接口、两端不同实现"的又一体现。

## A.3 `uni.connectSocket`（WebSocket 连接）

### 是什么

`uni.connectSocket` 是 uni-app 封装的 **WebSocket 客户端 API**，用来建立长连接。

- **App 端**：底层是 **原生 WebSocket**（`uni-webSocket` 插件，即 5+ Runtime 的原生 socket 实现）。
- **H5 端**：底层是浏览器 `WebSocket`。
- 返回一个 **`SocketTask`** 对象，后续操作（发消息、收消息、关闭）都挂在这个 task 上，而不是全局事件。

### 官方文档的关键点（本项目踩过的坑）

- **返回值是 `SocketTask`**，通过 `task.onOpen / onMessage / onError / onClose / send / close` 操作。
- **`header` 限制是 App 端的著名坑**：App 端原生 WebSocket **不认 `header` 里的 `Cookie`**——也就是说你在 `connectSocket({ header: { Cookie: '...' } })` 里塞 Cookie，App 端 WebSocket 握手时**不会带上它**，导致服务端鉴权失败。
  - 这正是本项目 `app.ts` 里 `setCookieToWebview()` 存在的原因：App 端要额外把 cookie 写进系统 `CookieManager`，原生 WebSocket 才会自动从系统层读到并带上（详见 A.10 和 B.4）。
  - H5 端没有这个问题：浏览器 WebSocket 会自动带上同源 cookie。

### 项目里具体怎么用

见 `src/api/ws.ts`（B.4 会逐段拆解），核心骨架：

```ts
task = uni.connectSocket({
  url: wsUrl(),        // 双端拼接方式不同（见 A.1 ③）
  header,              // App 端手动塞 Cookie（实际不生效，真正靠 CookieManager）
  complete: () => {},
});

task.onOpen(() => { openStream(); });      // 连上后发 open 帧
task.onMessage((res) => { onMessage(String(res.data)); }); // 收帧
task.onError(() => { finish('error'); });
task.onClose(() => { finish('close'); });
```

注意点：

- `res.data` 是字符串，要自己 `JSON.parse`。
- 项目里用 `complete: () => {}` 占位，只是为了统一 API 形状，实际没做任何事（连接成功与否交给 onOpen/onError 判断）。
- 断线后项目**没有自动重连**，只是 `finish('close')` 触发 `onDone` 回调提示"连接已断开"。这是个可改进点，下文 B.4 会再提。

## A.4 本地存储：`uni.getStorageSync` / `setStorageSync` / `removeStorageSync`

### 是什么

uni-app 封装的**跨端键值存储**，同步版本 API：

- `uni.setStorageSync(key, value)`：写入。
- `uni.getStorageSync(key)`：读取，读不到返回 `''`（空字符串）。
- `uni.removeStorageSync(key)`：删除。
- 也有异步版本 `uni.getStorage / setStorage / removeStorage`（带回调）。

### 官方文档的关键点

- **底层差异**：
  - **H5** → `localStorage`。
  - **App（Android）** → `SharedPreferences`；**App（iOS）** → `NSUserDefaults`。
  - 小程序 → `wx.setStorageSync`。
- **持久化**：应用退出、手机重启都不丢，只有卸载 App / 清除数据才没（H5 清浏览器缓存也会没）。
- **value 可以是对象/数组**：uni-app 会自动做序列化，不需要手动 `JSON.stringify`（但项目里为了稳妥，cookie 都显式 `String()` 过）。
- **key 大小写敏感、不要用特殊字符**。

### 项目里具体怎么用

封装在 `src/api/storage.ts`，把"裸 key"收敛成语义化函数：

```ts
// src/api/storage.ts
import { KEY_COOKIE, KEY_BASE_URL, KEY_TOKEN, DEFAULT_BASE_URL } from '../constants'

export function saveCookie(cookie: string) {
  uni.setStorageSync(KEY_COOKIE, cookie)   // 存鉴权 cookie（App 端用，H5 端由浏览器管）
}
export function loadCookie(): string {
  return uni.getStorageSync(KEY_COOKIE) || ''
}
export function saveBaseUrl(url: string) {
  uni.setStorageSync(KEY_BASE_URL, url)
}
export function loadBaseUrl(): string {
  return uni.getStorageSync(KEY_BASE_URL) || DEFAULT_BASE_URL
}
export function clearAuth() {
  uni.removeStorageSync(KEY_COOKIE)
  uni.removeStorageSync(KEY_TOKEN)
}
```

存储 key 统一定义在 `src/constants/index.ts`：

```ts
export const KEY_COOKIE = 'dsh_cookie'
export const KEY_BASE_URL = 'dsh_base_url'
export const KEY_TOKEN = 'dsh_token'
export const KEY_CONNECTED = 'connected'
```

项目里存了三样东西：

| key | 内容 | 用途 |
| --- | --- | --- |
| `dsh_cookie` | 鉴权 cookie | App 端手动带 Cookie、写 CookieManager |
| `dsh_base_url` | 桥/服务器地址 | auth/api/ws 拼接 URL 用 |
| `dsh_token` | 登录 token | 仅预填输入框（token 一次性，会失效） |
| `connected` | 是否已连接 | 启动时恢复连接状态点颜色 |

一个值得注意的点：**`dsh_token` 只用于预填输入框**，注释明确写了"token 是一次性的，会失效"，所以它不作为长期凭证——真正的凭证是换回来的 **cookie**。

## A.5 页面路由：`uni.navigateTo` / `redirectTo` / `reLaunch`

### 是什么

uni-app 的页面跳转 API，本质是操作**页面栈**（页面导航栈）。三个最常用：

| API | 行为 | 页面栈变化 | 场景 |
| --- | --- | --- | --- |
| `uni.navigateTo({ url })` | 跳转到应用内新页面，**保留当前页** | 压栈（栈 +1） | 需要"返回上一页" |
| `uni.redirectTo({ url })` | **关闭当前页**再跳转 | 出栈 + 入栈（栈不变） | 当前页使命完成，不希望用户返回它 |
| `uni.reLaunch({ url })` | **关闭所有页面**再打开目标页 | 清空栈，只剩目标页 | 回到首页、登录后重进主流程 |

配套的还有 `uni.navigateBack()`（返回上一页）、`uni.switchTab()`（跳 tabBar 页，本项目没用 tabBar）。

### 官方文档的关键点

- **`navigateTo` 有页面栈深度上限：最多 10 层**，超过会跳转失败。所以"列表→详情→详情"这种无限下钻不能用 navigateTo 一直堆。
- `url` 是页面路径（不带 `.vue` 后缀），**带参数用 query string**，例如 `'/pages/chat/chat?sessionId=xxx&title=yyy'`。
- 参数到目标页后，在 `onLoad(options)` 里通过 `options.sessionId` 取（见 A.7）。
- **`redirectTo` 不能跳 tabBar 页面**，`reLaunch` 可以。

### 项目里具体怎么用

三处典型用法，正好对应三种语义：

**① `navigateTo`：连接页 / 会话页（要能返回）**

`src/components/side-bar/side-bar.vue`：

```ts
function onConnect() {
  expanded.value = false;
  uni.navigateTo({ url: '/pages/connect/connect' }); // 保留当前页，可返回
}
```

`src/components/side-menu/side-menu.vue`：

```ts
function onSelect(e: SessionListItem) {
  global.setSession(e);
  const title = encodeURIComponent(e.projections?.values.title ?? '');
  uni.navigateTo({ url: `/pages/chat/chat?sessionId=${e.sessionId}&title=${title}` });
  expanded.value = false;
}
function onAddSession() {
  uni.navigateTo({ url: '/pages/session-create/session-create' });
}
```

**② `redirectTo`：创建完会话直接进聊天页（不希望返回创建页）**

`src/pages/session-create/session-create.vue`：

```ts
uni.redirectTo({ url: `/pages/chat/chat?sessionId=${sessionId}` });
```

创建页的使命是"建一个会话"，建完跳进 chat，用户按返回键不应再回到"创建页"（否则可能重复创建），所以用 redirectTo。

**③ `reLaunch`：返回键时清空栈、稳定回首页**

`src/pages/chat/chat.vue`：

```ts
onBackPress(() => {
  uni.reLaunch({ url: '/pages/index/index' });
  return true; // 阻止默认 navigateBack
});
```

chat 页可能是从 connect 页或 session-create 页跳进来的，页面栈里可能残留中间页。用 reLaunch 一次性清空栈回到 index，避免用户按返回时回到奇怪的中间页（或直接退出 App）。

> 补充：`return true` 是 `onBackPress` 的返回值约定，表示"已处理，阻止默认行为"，详见 A.7。

## A.6 `uni.showToast` / `uni.setNavigationBarTitle`（UI 提示）

### 是什么

- `uni.showToast`：弹出**轻提示**（toast），常用于成功/失败反馈。
- `uni.setNavigationBarTitle`：**动态设置页面标题**（原生导航栏上的文字）。

### 官方文档的关键点

**`uni.showToast`**：

- 参数：`title`（内容）、`icon`（`success` / `error` / `loading` / `none`）、`duration`（毫秒）、`mask`（是否透明遮罩防穿透点击）。
- **`icon: 'none'` 时 `title` 最多可显示两行**；带图标时标题有字数限制（超长会被截断）。
- 一次只能显示一个 toast，新的会顶掉旧的。

**`uni.setNavigationBarTitle`**：

- 参数 `{ title: string }`，动态改标题，比 `pages.json` 里的静态 `navigationBarTitleText` 更灵活。
- 只在**有原生导航栏**的页面生效（本项目 App/H5 都用默认原生导航栏）。

### 项目里具体怎么用

`src/pages/chat/chat.vue`：

```ts
// 发送失败提示（无图标，纯文字）
if (!ok) {
  uni.showToast({ title: '发送失败', icon: 'none' });
}

// 长连接断开提示
uni.showToast({ title: '连接已断开', icon: 'none' });

// onLoad 里根据 query 参数动态设标题
uni.setNavigationBarTitle({ title });
```

这里 `onLoad` 里拿到的 `title` 是从 `options.title` 解出的会话标题（`decodeURIComponent` 后），实现"标题栏跟着会话名走"，比 pages.json 里写死的"会话"二字更友好。

## A.7 页面生命周期：`onLoad / onReady / onUnload / onBackPress / onShow / onHide`

### 是什么

uni-app 的**页面**有自己的生命周期钩子，对应页面从创建到销毁的整个过程。Vue 3 组合式 API 下，需要从 `@dcloudio/uni-app` 里导入：

```ts
import { onLoad, onShow, onReady, onHide, onUnload, onBackPress } from '@dcloudio/uni-app';
```

### 官方文档的关键点（各钩子时机与用途）

| 钩子 | 触发时机 | 次数 | 本项目用途 |
| --- | --- | --- | --- |
| `onLoad(options)` | 页面加载，**能拿到路由参数** `options` | 一次 | 读 sessionId/title、订阅事件流 |
| `onShow` | 页面**每次显示**（从后台回前台、从别的页返回） | 多次 | 本项目未用 |
| `onReady` | 页面**首次渲染完成**，DOM 已就绪 | 一次 | 测量 scroll-view 高度 |
| `onHide` | 页面隐藏（跳走/切后台） | 多次 | 本项目未用 |
| `onUnload` | 页面卸载（被关闭） | 一次 | 取消 WebSocket 订阅 |
| `onBackPress` | 用户触发"返回"（安卓实体返回键 / 导航栏返回） | 每次返回 | 拦截返回、重定向到首页 |

几个官方文档重点：

- **`onLoad` 的 `options` 就是跳转 URL 里的 query 参数**，例如 `navigateTo({url:'/pages/chat/chat?sessionId=abc'})`，目标页 `onLoad((options) => options.sessionId === 'abc')`。
- **`onReady` 是拿 DOM 尺寸的安全时机**：此时页面已经渲染，`uni.createSelectorQuery` 能测到真实高度（A.13 详述）。
- **`onBackPress` 必须 `return true` 才能阻止默认返回行为**；返回 `false` 或不返回则走默认（navigateBack）。文档强调：onBackPress 只在"页面栈中还有页面"时能触发，且 tabBar 页面、首页等栈底页不触发。
- 组合式 API 的 `onShow`/`onHide` 与页面"从后台回前台/切后台"也有关联，适合做暂停/恢复。

### 项目里具体怎么用（chat.vue 是完整示例）

```ts
onLoad((options) => {
  const sid = options?.sessionId;
  if (!sid) return;
  sessionId.value = sid;
  const title = options?.title ? decodeURIComponent(options.title) : '会话';
  uni.setNavigationBarTitle({ title });

  // 订阅事件流：snapshot = 历史快照，event = 新事件，assistant-stream = 流式分片
  cancelFollow = followSession(sid, onFrame, onDone);
});

onReady(() => {
  measureViewHeight();   // 页面渲染完，测量 scroll-view 高度
});

onUnload(() => {
  cancelFollow?.();      // 离开页面，取消订阅，释放连接
});

onBackPress(() => {
  uni.reLaunch({ url: '/pages/index/index' });
  return true;           // 阻止默认 navigateBack
});
```

这段代码把生命周期职责分得很清楚：

- `onLoad` 做"初始化 + 建立连接"（连接只建一次）。
- `onReady` 做"依赖渲染结果的事"（量尺寸）。
- `onUnload` 做"清理资源"（断 WebSocket），防止离开页面后连接泄漏。
- `onBackPress` 做"返回行为控制"（跳首页）。

## A.8 App 生命周期：`onLaunch / onShow / onHide`（App.vue）

### 是什么

和"页面生命周期"不同，**App 生命周期**是整个应用级别，写在 `src/App.vue` 里，同样从 `@dcloudio/uni-app` 导入：

```ts

| 钩子 | 时机 |
| --- | --- |

| `onShow` | App 从后台进入前台（启动、从别的 App 切回都触发，**可多次**） |

### 项目里具体怎么用

`src/App.vue`（本项目目前只打日志占位）：

onShow(() => { console.log('App Show'); });

```

这里只是占位演示。若要扩展，`onLaunch` 里放"启动时从 storage 恢复连接状态"之类的逻辑是合理位置（本项目连接状态恢复放在了 `store/global.ts` 的 `state` 初始化里，见 A.9）。

- `page` 是 uni-app 页面根节点，H5 里映射为 `uni-page-body`，设 `height:100%` 才能让 `chat.vue` 里的 flex 布局正确撑满。

## A.9 Pinia（defineStore / state / actions / useXxxStore）

### 是什么

Pinia 是 Vue 3 官方的**状态管理库**，比 Vuex 更简洁、类型友好。uni-app Vue 3 项目官方推荐用它。

核心概念：

- `defineStore(id, options)`：定义一个 store，`id` 是唯一标识。
- `state`：存储响应式数据的函数（返回对象）。
- `actions`：修改状态、业务逻辑的方法。
- 组件里 `useXxxStore()`：拿到 store 实例，直接读写 `store.xxx` / 调 `store.method()`。

### 官方文档的关键点

- **注册**：在入口 `main.ts` 里 `app.use(createPinia())`，之后任何组件都能 `useXxxStore()`。
- **`state` 必须是函数**（返回对象），保证每个实例独立。
- **响应式**：直接读 `store.status` 是响应式的，改状态用 action（或直接赋值，Pinia 允许）。
- uni-app 里建议在 `onLoad` 等生命周期里调用 `useXxxStore()`，而非模块顶层（因为需要 pinia 已安装）。

### 项目里具体怎么用

**① 入口注册**（`src/main.ts`）：

```ts
import { createSSRApp } from 'vue';
import { createPinia } from 'pinia';
import App from './App.vue';

export function createApp() {
  const app = createSSRApp(App);
  app.use(createPinia());
  // 全局注册：模板里可用 {{ $formatTime(x) }}（相对时间格式化）
  app.config.globalProperties.$formatTime = (ts: number): string => { /* ... */ };
  return { app };
}
```

> 注意：uni-app Vue 3 用 `createSSRApp` 而非 `createApp`（SSR 兼容层，是 uni-app 的固定写法）。`globalProperties.$formatTime` 是给模板全局挂方法，`side-menu.vue` 里 `{{ $formatTime(item.updatedAt) }}` 就用到了它。

**② 定义 store**（`src/store/global.ts`）：

```ts
import { defineStore } from 'pinia';
import { KEY_CONNECTED } from '@/constants';

export type ConnStatus = 'disconnected' | 'unknow' | 'connected';

function getStatus(s: boolean) {
  if (s === true) return 'connected';
  else if (s === false) return 'disconnected';
  else return 'unknow';
}

export const useGlobalStore = defineStore('global', {
  state: () => {
    return {
      // 启动时从 storage 恢复连接状态（布尔/空 → 三态字符串）
      status: getStatus(uni.getStorageSync(KEY_CONNECTED)),
      session: null as SessionListItem | null,
    };
  },
  actions: {
    setStatus(s: boolean) { this.status = getStatus(s); },
    setSession(session: SessionListItem) { this.session = session; },
  },
});
```

设计要点：

- `status` 是**三态字符串**（红/黄/绿），由布尔值 `s` 映射而来。`getStorageSync` 读不到时返回 `''`（falsy），走 `else` 分支 → `'unknow'`（黄色"连接中/未知"）。
- store 里用 `null as SessionListItem | null` 给 `session` 标类型（当前选中的会话，供侧边栏 → 聊天页传递）。

**③ 组件里使用**（`src/components/side-bar/side-bar.vue`）：

```ts
import { useGlobalStore } from '../../store/global';
const global = useGlobalStore();

// computed 读取响应式状态
const dotClass = computed(() => ({
  red: global.status === 'disconnected',
  yellow: global.status === 'unknow',
  green: global.status === 'connected',
}));
```

`side-menu.vue` 里也用它判断"是否已连接"，决定显示会话列表还是"去连接"引导：

```ts
const connected = computed(() => global.status === 'connected');
```

## A.10 `plus.android` / CookieManager（App 端原生能力，importClass）

### 是什么

`plus` 是 5+ App 运行时暴露的**全局原生桥对象**（只有 App 端有，H5/小程序没有）。`plus.android` 提供 Android 原生能力访问，`plus.ios` 对应 iOS。

`android.webkit.CookieManager` 是 **Android WebView 的 cookie 存储管理器**。App 里 WebView 渲染层和原生网络层的 cookie 交互，就靠它。

### 官方文档的关键点

- `plus.android.importClass('包名.类名')`：**导入一个 Java 类**，返回一个"类对象"，用点号调用其静态方法/实例方法。
- `CookieManager.getInstance()`：拿到单例。
- 常用方法：
  - `setAcceptCookie(true)`：允许存储 cookie。
  - `setCookie(url, cookie)`：给指定 `url` 域设置 cookie 字符串。
  - `flush()`：把 cookie 落盘持久化。
  - `getCookie(url)`：读回该域的 cookie（用于验证）。
- **所有 plus.android 代码必须包在 `#ifdef APP-PLUS` 里**，否则 H5 打包运行报错。
- 类型上 `plus` 对象对 TS 不友好，项目里用 `(plus as any).android` 绕过类型检查。

### 项目里具体怎么用

`src/api/connect/app.ts` 里的 `setCookieToWebview()`：

```ts
// #ifdef APP-PLUS
function setCookieToWebview(cookie: string): void {
  try {
    const plusAndroid: any = (plus as any).android;
    // 1. 导入 Java 类
    const CookieManager = plusAndroid.importClass('android.webkit.CookieManager');
    // 2. 拿单例
    const cm = CookieManager.getInstance();
    // 3. 允许存 cookie
    cm.setAcceptCookie(true);
    // 4. 给桥地址写入 cookie（第一个参数是 URL，决定 cookie 的 domain）
    cm.setCookie(baseUrl(), cookie);
    // 5. 落盘
    cm.flush();
    console.log('[cookie] 已写入 CookieManager:', cookie.slice(0, 40));
    console.log('[cookie] 读回:', cm.getCookie(baseUrl()));
  } catch (e) {
    console.log('[cookie] setCookieToWebview 失败:', e);
  }
}
// #endif
```

**为什么必须做这一步？**（这是本项目最关键的 App 端知识点）

回顾 A.3：App 端原生 WebSocket 不认 `connectSocket` 的 `header.Cookie`。那 WebSocket 握手时怎么带上鉴权 cookie 呢？答案是：**原生 WebSocket 会去读系统 CookieManager 里该域的 cookie 自动附带**。所以拿到 cookie 后，要手动写一份进 CookieManager，WebSocket 才能连上。

注释原文：

```
原生 WebSocket（uni-webSocket 插件）不认 connectSocket 的 header.Cookie，
而是读系统 CookieManager；所以拿到 cookie 后要额外写一份进去，WebSocket 才能自动带上。
```

注意点：

- `setCookie(baseUrl(), cookie)` 的第一个参数是**带 scheme 的完整 URL**，cookie 的 domain 由它决定——必须和之后 WebSocket 连接的 URL 同域，才能匹配上。
- 项目里 `baseUrl()` 末尾会 `replace(/\/+$/, '')` 去掉多余斜杠，保证 URL 规整。
- 全程 `try/catch` 包裹，写入失败只打日志不抛异常（因为某些机型/系统可能限制，不能因为 cookie 写失败就整个连接崩掉）。

## A.11 easycom 组件自动注册（pages.json 的 easycom）

### 是什么

uni-app 的 **easycom 组件自动注册机制**：只要组件的文件名/目录满足约定，**不需要在页面里 `import` 和 `components` 注册**，模板里直接写 `<组件名 />` 就能用。

### 官方文档的关键点

- `easycom.autoscan: true`：自动扫描 `components/` 目录下的组件，按"目录名/组件名"约定自动注册。
- `easycom.custom`：**自定义匹配规则**，支持正则。官方 uni-ui 插件库的标准写法是：

```json
{
  "easycom": {
    "autoscan": true,
    "custom": {
      "^uni-(.*)": "@dcloudio/uni-ui/lib/uni-$1/uni-$1.vue"
    }
  }
}
```

这条规则含义：模板里凡是 `<uni-xxx>` 开头的组件，自动映射到 `@dcloudio/uni-ui` 包里的 `uni-xxx` 组件文件，无需手动引入。

- 优点：按需编译（只用到的组件才会打包）、少写一堆 import。
- 注意：easycom 只对 `components` 目录和 custom 规则匹配的组件生效；自定义组件名要避免和内置组件、HTML 标签冲突。

### 项目里具体怎么用

`src/pages.json` 顶部：

```json
{
  "easycom": {
    "autoscan": true,
    "custom": {
      "^uni-(.*)": "@dcloudio/uni-ui/lib/uni-$1/uni-$1.vue"
    }
  },
  "pages": [ ... ]
}
```

实际受益组件是 `session-create.vue` 里的 **`uni-data-select`**（下拉选择器）：

```vue
<template>
  <uni-data-select
    v-model="selectedModel"
    :localdata="modelOptions"
    placeholder="选择模型"
    :clear="false"
    :disabled="modelLoading"
  />
</template>
```

注意：`session-create.vue` 的 `<script setup>` 里**没有 import uni-data-select、也没有 components 注册**，全靠 easycom 自动解析。`autoscan: true` 同时还让项目自己的 `components/side-bar`、`components/side-menu`、`components/markdown-view` 自动注册——你在 `chat.vue`、`index.vue` 里直接写 `<side-menu />`、`<side-bar />`、`<markdown-view />` 而无需 import，也是 easycom 的功劳。

> 小提醒：`markdown-view` 里用到的 `mp-html` 是直接 `import MpHtml from 'mp-html/...vue'` 并局部注册的（见 A.14），没走 easycom，因为它不是 uni- 开头、也不在 components 目录的约定结构里。

## A.12 `defineOptions({ inheritAttrs: false })`（chat.vue 里为什么用）

### 是什么

`defineOptions` 是 **Vue 3.3+ 的编译宏**，用于在 `<script setup>` 里声明组件选项（原本只能在普通 `<script>` 块里写的选项，如 `name`、`inheritAttrs`、`emits` 声明等）。

`inheritAttrs: false` 是 Vue 组件的选项之一：**控制未被 `props` 声明的 attribute 是否自动透传到根元素**。

- 默认 `true`：父组件传来的、不在 props 里的 attribute（如 `title="xxx"`、`data-*`）会自动落到组件的根 DOM 元素上。
- `false`：不自动透传，这些 attribute 被收集到 `$attrs` 里由开发者自行处理。

### 官方文档的关键点

- `defineOptions` 是编译时宏，**不能使用运行时变量**（参数必须是静态字面量）。
- `inheritAttrs` 关闭后，`class` / `style` 仍会正常透传（Vue 特殊处理），其他 attribute 进 `$attrs`。
- 它常见于：封装组件不想让无关 attribute 污染根节点、或需要手动把 `$attrs` 派发到内部元素时。

### 项目里为什么用（chat.vue 的注释说得很清楚）

```ts
// 阻止 uni-app 把页面 query 参数（sessionId/title）透传到根元素，避免 title 变成浏览器 tooltip
defineOptions({ inheritAttrs: false });
```

背景：uni-app 会把页面路由的 **query 参数自动作为 attribute 透传给页面根组件**。也就是从 `side-menu.vue` 这样跳进来：

```ts
uni.navigateTo({ url: `/pages/chat/chat?sessionId=${e.sessionId}&title=${title}` });
```

uni-app 会把 `sessionId`、`title` 作为 attribute 挂在 chat 页面的根元素上。默认 `inheritAttrs: true` 时，这些 attribute 会落到根 `<view class="content">` 上：

- 后果 1：`title` 属性会让浏览器把它当 **HTML `title` 特性**，鼠标悬停时冒出原生 tooltip，体验怪异。
- 后果 2：根元素被塞进无关 attribute，语义不干净。

所以 `defineOptions({ inheritAttrs: false })` 关掉自动透传，query 参数只通过 `onLoad(options)` 正确读取（`options.sessionId` / `options.title`），不再污染 DOM。

> 这是本项目里一个很"细节控"的点，说明作者踩过 uni-app 页面参数透传到 DOM 的坑。值得一提：页面参数的正确读取入口始终是 `onLoad(options)`，而不是依赖 attribute 透传。

## A.13 `uni.createSelectorQuery`（测量 DOM 尺寸）

### 是什么

uni-app 提供的 **DOM 节点信息查询 API**，等价于小程序的 `wx.createSelectorQuery` / H5 的 `getBoundingClientRect`，用来**获取页面节点的位置、尺寸、滚动位置**等信息。

### 官方文档的关键点

- 基本用法：`uni.createSelectorQuery().select('.xxx').boundingClientRect(cb).exec()`。
  - `select(selector)`：选一个匹配的节点（CSS 选择器）。
  - `boundingClientRect(cb)`：查询布局信息，回调里拿到 `{ left, top, width, height, scrollLeft, scrollTop }`。
  - `exec()`：**必须调用才真正执行查询**（前面都是声明式链式调用）。
- **必须在页面渲染完成后调用**（`onReady` 或之后），否则节点还没渲染，拿到的是空/0。
- 还有 `selectAll`（多节点）、`scrollOffset`（查滚动）、`fields`（查更多字段）等。
- App 端返回的尺寸单位是 **px**，注意和 rpx 的换算。

### 项目里具体怎么用

`chat.vue` 用它量 scroll-view 的可视高度，做"沉底滚动"判断：

```ts
let viewHeight = 0; // scroll-view 可视高度（onReady 测量）

function measureViewHeight() {
  uni
    .createSelectorQuery()
    .select('.msg-list')          // 选中消息列表 scroll-view
    .boundingClientRect((rect: any) => {
      if (rect && rect.height > 0) viewHeight = rect.height;  // 存可视高度
    })
    .exec();                        // 真正执行
}

onReady(() => {
  measureViewHeight();             // 渲染完成后再测，保证拿得到
});
```

拿到 `viewHeight` 后，`onScroll` 里用它判断用户是否"沉底"：

```ts
function onScroll(e: any) {
  const top = e.detail?.scrollTop ?? 0;         // 已滚动距离
  const sh = e.detail?.scrollHeight ?? 0;        // 内容总高度
  if (viewHeight > 0 && sh > 0) {
    // 距底部 < 50px 视为沉底
    stickToBottom.value = sh - top - viewHeight < 50;
  }
}
```

判断逻辑：`scrollHeight - scrollTop - viewHeight` 就是"距底部还剩多少"，小于 50px 认为沉底。这个 `stickToBottom` 用于实现"AI 流式输出时自动滚到底，但用户手动上翻历史时不要抢滚动"（详见 B.5）。

### ② `mp-html` + `markdown-it`（Markdown 渲染）

`markdown-view.vue` 把 AI 回复的 Markdown 转 HTML 再交给 `mp-html` 渲染：

```ts
import MpHtml from 'mp-html/dist/uni-app/components/mp-html/mp-html.vue';
import MarkdownIt from 'markdown-it';

const md = new MarkdownIt({

## B.1 token 换 cookie 完整流程（app.ts 的 `connect()`）

### 背景：为什么 App 端不能像 H5 那样"自动存 cookie"

- H5 端跑在浏览器里，`fetch('/auth?token=xxx')` 后，DSH 返回 `302/303 + Set-Cookie`，**浏览器自动跟随重定向并保存 cookie**，后续请求浏览器自动带上。代码只要 `fetch` 一次就行（`H5.ts` 里的 `connect()` 就是这么简单）。
- App 端没有浏览器这套自动机制，`uni.request` 拿到 `Set-Cookie` 响应头后，**没人帮你存、也没人帮你带**。所以必须：
  1. 通过桥 `/auth` 换出 cookie 文本。
  2. 存进 storage。
  3. 写进系统 CookieManager（供 WebSocket 用）。
  4. 之后每次 HTTP 请求**手动在 header 塞 Cookie**。

### 逐段拆解

```ts
async connect(token: string): Promise<ConnectResult> {
  uni.removeStorageSync(KEY_COOKIE);   // ① 先清掉旧 cookie，避免脏数据
  return new Promise((resolve) => {
    // ② 通过桥拿 cookie：桥用 Node http 抓 DSH 303 上的 set-cookie，返回 JSON { ok, cookie }
    console.log('[connect] 服务器地址:', baseUrl());
    uni.request({
      url: `${baseUrl()}/auth?token=${encodeURIComponent(token)}`,  // ③ 请求桥的 /auth
      method: 'GET',
      success(result) {
        const data = result.data as any;
        if (result.statusCode === 200 && data?.ok && data.cookie) {
          // ④ 换 cookie 成功
          const cookie = String(data.cookie);
          uni.setStorageSync(KEY_COOKIE, cookie);      // ⑤ 存 storage（HTTP 手动带）
          // #ifdef APP-PLUS
          setCookieToWebview(cookie);                  // ⑥ 写 CookieManager（WebSocket 用）
          // #endif
          resolve({ ok: true, message: '连接成功' });
        } else if (result.statusCode === 401 || data?.status === 401) {
          resolve({ ok: false, message: 'token 无效' });   // ⑦ token 无效
        } else {
          resolve({ ok: false, message: `连接失败（HTTP ${result.statusCode}）` });
        }
      },
      fail(e) {
        resolve({ ok: false, message: `桥连接失败：${e.errMsg}` });  // ⑧ 网络层失败
      },
    });
  });
}
```

逐步说明：

1. **① 清旧 cookie**：`removeStorageSync(KEY_COOKIE)`。防止上次的失效 cookie 残留，导致后续请求带错凭证。

2. **③ 请求桥的 `/auth`**：注意这里请求的是**桥地址**（`baseUrl()`，默认 `http://192.168.8.219:3081`），不是直接请求 DSH（3080）。为什么走桥？看 `bridge.js`：

```js
if (u.pathname === '/auth' && u.searchParams.has('token')) {
  const token = u.searchParams.get('token');
  const dsh = http.get({
    hostname: DSH_HOST,      // 192.168.8.219
    port: DSH_PORT,          // 3080
    path: `/?token=${encodeURIComponent(token)}`,
    headers: { Host: DSH_AUTHORITY },   // 关键：Host 用白名单里的值
  }, (r) => {
    const sc = r.headers['set-cookie'];
    if (sc) {
      const cookie = String(Array.isArray(sc) ? sc[0] : sc).split(';')[0];  // 只取 "k=v" 那段
      res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
      res.end(JSON.stringify({ ok: true, cookie }));
    } else {
      res.writeHead(r.statusCode || 500, { ... });
      res.end(JSON.stringify({ ok: false, status: r.statusCode || 500 }));
    }
  });
}
```

桥做的事：

- 直连 DSH（`/?token=xxx`），把 `Host` 头**改成白名单里的 `192.168.8.219:3080`**，绕过 DSH 的 Host/Origin 防火墙。
- 从 DSH 响应里抓 `set-cookie`，**只截取 `k=v` 部分**（`split(';')[0]`，丢掉 Path/HttpOnly/Expires 等属性）。
- 包装成 `{ ok: true, cookie: 'dsid=xxxx' }` 返回给 App。

3. **④⑤⑥ 三连动作**：拿到 cookie 后：
   - `setStorageSync(KEY_COOKIE, cookie)`：存 storage，`send()` 里读它手动带 Cookie。
   - `setCookieToWebview(cookie)`：写系统 CookieManager（A.10 已拆解），供原生 WebSocket 自动带上。

4. **⑦⑧ 错误分档**：`401`（或 body 里 `status===401`）明确提示"token 无效"；其他状态码提示 HTTP 状态；`fail` 是网络层失败（连不上桥）。

### 换 cookie 之后的"验证"步骤

`connect()` 换完 cookie 不算完，`client.ts` 的 `connect()` 还会**用 cookie 调一次 `session/list` 验证凭证是否真生效**：

```ts
export async function connect(token: string): Promise<ConnectResult> {
  const global = useGlobalStore();
  // 1. token 交换（换 cookie）
  const connectResult = await connectFunction.connect(token);
  if (!connectResult.ok) {
    global.setStatus(false);
    return connectResult;
  }
  // 2. 用 cookie 调 session/list 验证
  let res = await connectFunction.send(HttpMethodList.list, {});
  global.setStatus(res?.result?.ok);
  uni.setStorageSync(KEY_CONNECTED, res?.result?.ok);
  if (res?.result?.ok) {
    const items: unknown[] = res.result.value?.items ?? [];
    return { ok: true, message: `连接成功，共 ${items.length} 个会话`, sessionCount: items.length };
  }
  return { ok: false, message: 'token 无效或鉴权失败' };
}
```

为什么多此一举？因为 `/auth` 返回 200 只说明"桥换到了 cookie"，不代表 cookie 一定有效。真正能证明"连上了"的是**用这个 cookie 成功调通一个受保护接口**（`session/list`）。这一步同时把"连接状态"写进 store 和 storage，供侧边栏状态点用。

## B.2 手动带 Cookie 的 HTTP 请求（app.ts 的 `send()`）

### 逐段拆解

```ts
async send(method: string, request: object): Promise<any> {
  const cookie = uni.getStorageSync(KEY_COOKIE) || '';   // ① 从 storage 读 cookie
  const header: Record<string, string> = { 'Content-Type': 'application/json' };
  if (cookie) header.Cookie = cookie;                     // ② 手动塞 Cookie 头

  const res = await uni.request({
    url: `${baseUrl()}/api/${method}`,   // ③ 桥地址 + 方法路径，如 /api/session/list
    method: 'POST',
    header,                               // ④ header 注意是单数
    data: buildRequest(method, request),  // ⑤ 请求体用 RPC 信封（B.3 讲）
  });
  console.log('[send]', method, 'HTTP', res.statusCode, '| body:', JSON.stringify(res.data).slice(0, 200));
  return res.data;                        // ⑥ 直接返回响应体
}
```

逐步说明：

1. **①② 手动带 Cookie**：这是 App 端和 H5 端最本质的区别。H5 端 `fetch` 会自动带同源 cookie；App 端 `uni.request` 不会，所以每次请求都从 storage 读 cookie、手动塞进 `header.Cookie`。cookie 为空（未连接）就不塞，请求会以"未鉴权"状态发出，由服务端返回 401。

2. **③ 请求桥的 `/api/{method}`**：同样走桥（`baseUrl()` 是桥地址），桥收到后转发给 DSH 并改 Host：

```js
// bridge.js：API 转发
if (u.pathname.startsWith('/api/')) {
  const fwdHeaders = { ...req.headers, Host: DSH_AUTHORITY };  // 改 Host 为白名单值
  for (const h of ['origin', 'sec-fetch-site', 'sec-fetch-mode', 'sec-fetch-dest', 'referer']) {
    delete fwdHeaders[h];   // 剥掉可能触发 DSH 防火墙的浏览器安全头
  }
  const proxyReq = http.request({ hostname: DSH_HOST, port: DSH_PORT, path: req.url, method: req.method, headers: fwdHeaders }, ...);
  req.pipe(proxyReq);       // 请求体透明转发
}
```

   关键点：桥**原样透传 Cookie**（`...req.headers` 里就有 App 手动塞的 Cookie），所以 App 只要在 header 带上 Cookie，经过桥后仍会到达 DSH。

3. **⑤ 请求体是 RPC 信封**：`buildRequest()` 生成，不是直接 `request` 对象。这是 DSH 的协议要求，下一节拆解。

4. **⑥ 返回 `res.data`**：上层 `client.ts` 各方法统一从 `res.result.ok` / `res.result.value` 取数据（见 B.1 的验证代码和 `getList` 等）。

## B.3 RPC 请求信封（rpc.ts 的 `buildRequest`）

### 信封结构

DSH 用的是 **Typert RPC**（一种类型安全的 RPC 协议）。每次 HTTP 调用，请求体不是裸参数，而是一个固定结构的"信封"：

```ts
export interface RpcRequest<T = Record<string, unknown>> {
  type: 'client-request'   // 帧类型：客户端请求
  rpcId: string            // 请求 id（自增，用于匹配请求/响应）
  method: string           // 方法名，如 'session/list'
  payload: { args: Record<string, T> }  // 参数包装
}
```

### 逐段拆解 `buildRequest`

```ts
let seq = 0

function nextRpcId(): string {
  seq += 1
  return String(seq)   // '1' → '2' → '3' ... 自增字符串
}

export function buildRequest<T extends object>(method: string, request: T): RpcRequest<T> {
  const isList = method === HttpMethodList.list                     // 'session/list'
  // 无参方法不能带 request 字段，否则 Typert 严格校验会拒绝
  const isNoArg =
    method === HttpMethodList.modelCatalog ||                        // 'session/modelCatalog'
    method === HttpMethodList.agentPresetsList                       // 'agentPresets/list'

  const args: any = isNoArg
    ? {}                                  // 无参方法：args 为空对象
    : isList
      ? { _request: request }             // list：参数名特殊，是 _request
      : { request: request }              // 其他方法：参数名是 request

  return {
    type: 'client-request',
    rpcId: nextRpcId(),
    method,
    payload: { args },
  }
}
```

### 三种参数形态（重点记忆）

`args` 里参数名不是随便起的，Typert 按方法签名严格校验：

| 方法 | 参数形态 | 原因 |
| --- | --- | --- |
| `session/list` | `{ _request: request }` | list 的参数名就叫 `_request` |
| `session/modelCatalog`、`agentPresets/list` | `{}`（不带任何字段） | 无参方法，带了 request 字段会被严格校验拒绝 |
| 其他（`session/create`/`prompt`/`page`/`selectModel`） | `{ request: request }` | 常规参数名是 `request` |

看几个实际拼出来的信封（配合 `client.ts`）：

`getList()` → `send('session/list', {})`：

```json
{
  "type": "client-request",
  "rpcId": "1",
  "method": "session/list",
  "payload": { "args": { "_request": {} } }
}
```

`sendPrompt()` → `send('session/prompt', param)`：

```json
{
  "type": "client-request",
  "rpcId": "2",
  "method": "session/prompt",
  "payload": { "args": { "request": { "requestId": "...", "sessionId": "...", "mode": "queue", "content": [...] } } }
}
```

`getModelCatalog()` → `send('session/modelCatalog', {})`：

```json
{
  "type": "client-request",
  "rpcId": "3",
  "method": "session/modelCatalog",
  "payload": { "args": {} }
}
```

> 结论：`buildRequest` 的核心价值是**统一封装 + 按方法名分派参数名**，把 Typert 的严格校验细节藏起来，上层 `client.ts` 只管传业务参数。

### 上层 `client.ts` 如何组织方法

`client.ts` 是"业务 API 层"，把 HTTP 方法名、请求参数、返回值类型全部收口，页面只调这些函数：

```ts
export async function getList(): Promise<SessionListItem[]> {
  let res = await connectFunction.send(HttpMethodList.list, {});
  if (res?.result?.ok) {
    const list: SessionListValue = res?.result?.value;
    if (list) return list.items;
  }
  return [];
}

export async function sendPrompt(sessionId: string, text: string): Promise<boolean> {
  const param: SessionPromptRequest = {
    requestId: nextRequestId(),
    sessionId,
    mode: 'queue',
    content: [{ type: 'text', text }],
  };
  const res = await connectFunction.send(HttpMethodList.prompt, param);
  return res?.result?.ok === true;
}
```

方法名常量集中在 `src/constants/index.ts`（`HttpMethodList`），避免散落字符串：

```ts
export const HttpMethodList = {
  list: 'session/list',
  create: 'session/create',
  prompt: 'session/prompt',
  selectModel: 'session/selectModel',
  modelCatalog: 'session/modelCatalog',
  page: 'session/page',
  agentPresetsList: 'agentPresets/list',
  // ...
} as const
```

`session/prompt` 有个细节：它只是把消息**排队发送**（`mode: 'queue'`），返回 `accepted: true` 表示"已接受排队"，**真正的 AI 回复不走这个 HTTP 接口，而是走 WebSocket 流式下发**（下一节）。

## B.4 WebSocket mux 协议（ws.ts 的 `followSession`）

### 协议总览（注释里已确认）

```text
端点：/api/remote.mux（一个物理 WebSocket 复用多条逻辑流）

客户端帧：open(streamId, endpoint, payload) / item / end / cancel
服务端帧：item(streamId, value) / end / error

session/follow 的 payload = { args: { request: { address, assistantStream, ... } } }
返回帧 value 三种：
  snapshot          —— 历史快照（一次性补历史）
  event             —— 新事件（如 assistant/message 整段提交）
  assistant-stream  —— 流式分片（打字机）

assistant-stream 帧内部又分：start / chunk / end
  chunk 细分：text-delta（正文增量）/ reasoning-delta（思考增量）/ tool-call-delta / block-* / usage / finish
```

关键概念：**"mux"= 多路复用**。一个物理 WebSocket 连接上，用 `streamId` 区分多条逻辑流。每条逻辑流是独立的一次 `session/follow` 订阅，互不干扰。

### 逐段拆解 `followSession`

**① 函数签名与取消机制**

```ts
export function followSession(
  sessionId: string,
  onFrame: (frame: unknown) => void,   // 收到 follow 帧时回调（snapshot/event/assistant-stream）
  onDone?: () => void,                 // 流结束（end/error/close）回调
): () => void {
  const streamId = `s-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`;  // 唯一流 id
  let closed = false;                  // 防止重复 finish
  let task: UniApp.SocketTask | null = null;

  const finish = (reason?: string) => {  // 统一收尾：只跑一次
    if (closed) return;
    closed = true;
    try { task?.close({}); } catch { /* noop */ }
    onDone?.();
  };
```

- 返回 `finish` 函数作为**取消订阅的句柄**（`chat.vue` 的 `cancelFollow` 就是它）。
- `closed` 标志保证 `end`、`error`、`close` 三个可能重复触发的地方只执行一次收尾。

**② open 帧：开流**

```ts
const openStream = () => {
  task?.send({
    data: JSON.stringify({
      type: 'open',
      streamId,                          // 本逻辑流的 id
      endpoint: WebSocketMethodList.follow,   // 'session/follow'
      payload: {
        args: {
          request: {
            address: { kind: 'session', sessionId },   // 订阅哪个会话
            assistantStream: true,        // 关键：开启流式，assistant-stream 帧逐段下发
          },
        },
      },
    }),
  });
};
```

- WebSocket 帧的 `payload` 结构与 HTTP RPC 信封**同构**（`args.request` 包参数），只是外层换成了 `type: 'open'` + `streamId` + `endpoint`。
- `assistantStream: true` 是"打字机效果"的开关：不传这个字段，DSH 会整段输出（没有 assistant-stream 分片）。

**③ 收帧与过滤**

```ts
const onMessage = (raw: string) => {
  let msg: any;
  try { msg = JSON.parse(raw); } catch { return; }   // 非 JSON 忽略
  if (msg?.streamId !== streamId) return;             // 只处理本流
  if (msg.type === 'item') {
    onFrame(msg.value);                               // 把 value 交给上层（snapshot/event/assistant-stream）
  } else if (msg.type === 'end' || msg.type === 'error') {
    finish(`frame:${msg.type}`);                      // 流结束
  }
};
```

- **`streamId` 过滤是 mux 的核心**：同一物理连接上可能有别的逻辑流的帧，只认自己的。
- `item` 帧的 `value` 就是上层要的 `snapshot` / `event` / `assistant-stream` 之一。

**④ 建立连接（含 App 端 cookie 处理）**

```ts
let header: Record<string, string> = {};
// #ifdef APP-PLUS
const cookie = uni.getStorageSync(KEY_COOKIE);
if (cookie) header = { Cookie: String(cookie) };   // 手动塞（实际 App 原生 WS 不认，真正靠 CookieManager）
// #endif

task = uni.connectSocket({
  url: wsUrl(),    // 双端拼接（见 A.1 ③）
  header,
  complete: () => {},
});

task.onOpen(() => { openStream(); });        // 连上后立刻发 open 帧开流
task.onMessage((res) => { onMessage(String(res.data)); });
task.onError(() => { finish('error'); });
task.onClose((res: any) => { finish('close'); });
```

- App 端 `header` 里塞 Cookie 其实是"保险动作"（有些版本/平台可能生效），**真正让 WebSocket 带上 cookie 的是 B.1 里写的 CookieManager**（A.3、A.10 已详述）。
- H5 端 `header` 为空，浏览器自动带同源 cookie。

**⑤ URL 拼接**

```ts
function wsUrl(): string {
  // #ifdef H5
  const proto = location.protocol === 'https:' ? 'wss:' : 'ws:';
  return `${proto}//${location.host}/api/remote.mux`;   // 同源走 Vite proxy
  // #endif
  // #ifdef APP-PLUS
  const base = String(uni.getStorageSync(KEY_BASE_URL) || '');
  return base.replace(/^http/, 'ws') + '/api/remote.mux';   // 桥地址 http→ws
  // #endif
}
```

- App 端：把桥地址 `http://192.168.8.219:3081` 变成 `ws://192.168.8.219:3081/api/remote.mux`。
- 桥收到 WebSocket upgrade 请求后，做透明字节管道转发（`bridge.js` 的 `server.on('upgrade')`），同样改 Host、剥安全头、透传 Cookie。

### 一个可改进点

`onClose` 直接 `finish('close')`，**没有自动重连**。移动端网络抖动很容易断线，生产环境建议加"指数退避重连"（断线后延迟重连、失败递增延迟）。这是本项目当前留下的 TODO 级缺口，读代码时可以注意。

## B.5 流式打字机渲染（chat.vue）

### 数据流全景

```
WebSocket followSession
   │
   ├─ value.type === 'snapshot'         → toBubbles(records) 覆盖历史气泡
   ├─ value.type === 'event'
   │    └─ event.type === 'assistant/message' → 整段提交（把 live 标为 done）
   └─ value.type === 'assistant-stream' → handleAssistantStream
                                            ├─ start  → 初始化 liveStream
                                            ├─ chunk(text-delta) → 追加文本 + 沉底滚动
                                            └─ end    → outcome≠committed 时清空
```

### 核心状态

```ts
const sessionId = ref('');

const draft = ref('');
const sending = ref(false);

设计要点：

- `bubbles` 是"已完成"的历史消息；`liveStream` 是"正在输入"的那条 live 消息，二者**分开展示**（模板里两个渲染块），避免流式追加时频繁重建整个历史。
- `liveStream.done` 标志：流式过程中 `done=false`（按块 + 尾巴渲染）；完成后 `done=true`（整段按 Markdown 渲染）。

### 模板里的两段渲染

关键：live 消息里**已完成块各自一个 `<markdown-view>`**（一旦成块就固定，后续不重渲染），只有**尾巴**是纯文本实时更新——这样避免每个 chunk 到来都重解析整段 Markdown 导致的闪烁和性能问题。

### 块级切分 `splitStreaming`（切块的难点）

```ts
function splitStreaming(text: string): { blocks: string[]; tail: string } {
  if (!text) return { blocks: [], tail: '' };
  const lines = text.split('\n');
  const boundaries: number[] = [];   // 安全空行（不在代码围栏内）的索引
  let inFence = false;
  for (let i = 0; i < lines.length; i++) {
    const line = lines[i];
    if (/^\s*```/.test(line) || /^\s*~~~/.test(line)) {
      inFence = !inFence;    // 进出代码围栏
      continue;
    }
    if (!inFence && line.trim() === '') boundaries.push(i);  // 围栏外的空行 = 切块边界
  }
  if (boundaries.length === 0) return { blocks: [], tail: text };
  const lastBoundary = boundaries[boundaries.length - 1];
  const blocks: string[] = [];
  let start = 0;
  for (const b of boundaries) {
    const block = lines.slice(start, b).join('\n').trim();
    if (block) blocks.push(block);
    start = b + 1;
  }
  return { blocks, tail: lines.slice(lastBoundary + 1).join('\n') };
}
```

逻辑：

- **按空行把文本切成"段落块"**，已经完整的段落各自进 `blocks`，最后一个还没结尾的段落进 `tail`。
- **代码围栏（``` / ~~~）内的空行不切**：用 `inFence` 状态机跟踪，避免把代码块内部的空行误当段落边界，破坏 Markdown 结构。
- 这样"正在输入的半句话"在 `tail` 里以纯文本展示，写满一个空行后该段落到 `blocks` 里转成 Markdown 渲染。

`liveParts` 计算属性把状态翻译成渲染数据：

```ts
const liveParts = computed(() => {
  const s = liveStream.value;
  if (!s) return { blocks: [] as string[], tail: '' };
  if (s.done) return { blocks: s.text.trim() ? [s.text] : [], tail: '' };  // 完成：整段一个块
  return splitStreaming(s.text);   // 流式：切块 + 尾巴
});
```

### 处理 assistant-stream 帧

```ts
function handleAssistantStream(f: any) {
  if (!f) return;
  if (f.type === 'start') {
    // 仅在新回复开始时初始化；同一回复的后续 attempt 不清空已累积文本
    if (!liveStream.value) liveStream.value = { text: '', done: false };
  } else if (f.type === 'chunk') {
    const chunk = f.chunk;
    if (chunk?.type === 'text-delta' && typeof chunk.text === 'string') {
      if (!liveStream.value) liveStream.value = { text: '', done: false };
      const atBottom = stickToBottom.value;   // 追加前是否在底部
      liveStream.value.text += chunk.text;    // 追加增量文本
      if (atBottom) scrollToBottom(true);     // 在底部才自动滚动
    }
    // 忽略 reasoning-delta / tool-call-delta / block-start / block-end / usage / finish
  } else if (f.type === 'end') {
    // committed 由随后的 assistant/message 事件收尾；非 committed（中止/steer）清空
    if (f.outcome?.kind !== 'committed') liveStream.value = null;
  }
}
```

要点：

- **`start` 只初始化一次**：`if (!liveStream.value)` 保证同一回复的重试/换 attempt 不清空已累积文本。
- **`chunk` 里只消费 `text-delta`**（正文增量），其他增量类型（`reasoning-delta` 思考过程、`tool-call-delta` 工具调用）本项目**忽略**——只展示最终正文，不展示思考/工具细节。
- **`end` 的语义**：`outcome.kind === 'committed'` 表示内容已提交，会由后续的 `assistant/message` **事件**做最终整段收尾（此时不在这里动）；否则（中止/steer 改写）直接把 live 清空。

### 整段提交（event: assistant/message）

```ts
} else if (frame?.type === 'event' && frame.event?.type === 'assistant/message') {
  // 整段提交：把 live 流标为完成，仍用同一元素渲染，避免切换闪烁
  const text = textOf(frame.event?.data?.message?.content);
  const atBottom = stickToBottom.value;
  if (liveStream.value) {
    liveStream.value = { text: text || liveStream.value.text, done: true };  // 用最终完整文本覆盖，标完成
    if (atBottom) scrollToBottom(true);
  } else if (text) {
    appendAssistant(text);   // 没有 live（比如纯工具回复）→ 直接追加历史气泡
  }
}
```

这里很巧妙：流式分片结束后，DSH 会再发一个 `assistant/message` **事件**携带最终完整文本。代码不新建气泡，而是**把 liveStream 的 text 换成最终文本、标 `done=true`**，让同一个元素从"流式态"平滑过渡到"完成态"，避免切换闪烁。

### 历史快照（snapshot）

```ts
if (frame?.type === 'snapshot') {
  bubbles.value = toBubbles(frame.records ?? []);   // 事件流 → 气泡列表（B.6）

```

进入页面先收到一次 `snapshot`（历史快照），用 `toBubbles` 转成气泡列表，之后才是增量 `event` / `assistant-stream`。

### 沉底滚动（用户体验关键）

```ts
function onScroll(e: any) {
  const top = e.detail?.scrollTop ?? 0;
  const sh = e.detail?.scrollHeight ?? 0;
  if (viewHeight > 0 && sh > 0) {
    stickToBottom.value = sh - top - viewHeight < 50;   // 距底 <50px 视为沉底
  }
}

function scrollToBottom(force = false) {
  if (!force && !stickToBottom.value) return;   // 用户上翻时不强制沉底
  nextTick(() => {
    scrollBottomTick += 1;
    scrollTopValue.value = 100000000 + scrollBottomTick;   // 递增大值，clamp 到最底部
  });
}
```

- **沉底判断**：`onScroll` 实时更新 `stickToBottom`。用户在底部附近 → `true`；用户往上翻历史 → `false`。
- **智能滚动**：流式追加时 `scrollToBottom(true)` 强制滚底（发消息、收到快照）；但 `handleAssistantStream` 里用 `if (atBottom) scrollToBottom(true)`——**只有用户本来就沉底才自动滚**，避免用户正在翻历史时被硬拽到底部。
- **递增大值触发滚动**：`scroll-top` 每次变化都会触发 scroll-view 滚动，设 `100000000 + tick` 的递增大值（每次 +1 保证值变化），会被 clamp 到最底部，可靠触发"滚到底"。

### 发送流程（乐观渲染 + 排队）

```ts
async function onSend() {
  const text = draft.value.trim();
  if (!text || !sessionId.value || sending.value) return;
  sending.value = true;
  draft.value = '';
  commitLive();        // 固化上一条 live 消息
  appendUser(text);    // 乐观渲染：先显示用户消息
  const ok = await sendPrompt(sessionId.value, text);   // HTTP 排队发送
  sending.value = false;   // 发送完就恢复；回复走 WebSocket，不影响后续发送
  if (!ok) {
    uni.showToast({ title: '发送失败', icon: 'none' });
  }
}
```

- **乐观渲染**：先 `appendUser(text)` 把用户消息画出来，再发请求，体验即时。
- **`commitLive`**：发新消息前，把上一条 live assistant 消息固化进历史 `bubbles`，清空 `liveStream`，避免新旧消息混在一起。
- **`sending=false` 提前恢复**：因为 `sendPrompt` 只是排队发送（返回 `accepted`），真正的回复异步走 WebSocket，所以不需要等回复完成就能再发下一条。

## B.6 事件流转气泡（history.ts 的 `toBubbles`）

### 分层模型（两层）

先理解"两层数据模型"，这是 `history.ts` 的核心设计：

```
原始事件流（SessionPageRecord[]）  ──toBubbles()──►  气泡列表（Bubble[]）
    turn/start, user/message,                          ├─ UserBubble（用户气泡）
    assistant/message, tool/call,                      └─ AssistantBubble（AI 回复气泡）
    tool/result, system/message, ...                        └─ parts[]（内部片段）
                                                                ├─ text（文字）
                                                                ├─ tool-call（工具调用）
                                                                ├─ tool-result（工具结果）
                                                                └─ system（系统）
```

```ts
export type Bubble = UserBubble | AssistantBubble;

export interface UserBubble {
  role: 'user';
  seq: number;      // 事件序号
  time: number;     // 时间戳
  turn?: number;    // 所属轮次
  text: string;     // 用户文字
}

export interface AssistantBubble {
  role: 'assistant';
  seq: number; time: number; turn?: number;
  parts: AssistantPart[];   // 内部多个片段
}

export type AssistantPart =
  | (AssistantPartBase & { kind: 'text'; text: string })
  | (AssistantPartBase & { kind: 'tool-call'; name: string; args: string })
  | (AssistantPartBase & { kind: 'tool-result'; text: string; isError?: boolean })
  | (AssistantPartBase & { kind: 'system'; text: string });
```

职责边界注释也写得很清楚：

```text
client.ts   → getHistory() 发 HTTP、拿 SessionPageValue
history.ts  → toBubbles() 把事件流转成 Bubble[]
chat.vue    → 渲染 Bubble[]
```

### 逐段拆解 `toBubbles`

**① 状态变量**

```ts
export function toBubbles(records: SessionPageRecord[]): Bubble[] {
  const bubbles: Bubble[] = [];
  let parts: AssistantPart[] = [];   // 攒着还没落地的 AI parts
  let startSeq = 0;                  // 当前 AI 气泡的起始 seq
  let startTime = 0;                 // 起始时间
  let currentTurn: number | undefined;   // 当前轮次

  // 把攒着的 parts 落成一个 AI 回复气泡
  const flush = () => {
    if (parts.length === 0) return;
    bubbles.push({ role: 'assistant', seq: startSeq, time: startTime, turn: currentTurn, parts });
    parts = [];
  };
```

- `parts` 是"缓冲区"：AI 回复由多个事件组成（先工具调用、再工具结果、再文字……），先把这些 part 攒起来，等一轮结束（`turn/end` 或遇到下一条 user/message）再 `flush` 成**一个** AI 气泡。
- `flush` 只在 `parts` 非空时才落气泡。

**② 遍历事件 + 分组 switch**

```ts
for (const r of records) {
  const e = r.event;
  const d = e.data as any;
  const step = typeof d?.step === 'number' ? (d.step as number) : undefined;

  switch (e.type) {
    case 'turn/start':
      currentTurn = typeof d?.turn === 'number' ? (d.turn as number) : undefined;
      flush();   // 新的一轮开始，把上一轮的 AI 回复先落下去
      break;

    case 'turn/end':
      flush();   // 本轮结束，AI 回复到此为止
      currentTurn = undefined;
      break;

    case 'user/message':
      // DSH 注入的多条 role=user 消息（agent-instructions / runtime-context / skill-catalog）
      // 只有 source.kind === 'user' 才是用户真正输入的内容
      if (d?.source?.kind !== 'user') break;
      flush();   // 用户消息前，先把之前攒的 AI 回复发出去
      bubbles.push({ role: 'user', seq: e.seq, time: e.time, turn: currentTurn, text: textOf(d?.content) });
      break;

    case 'assistant/message': {
      const text = textOf(d?.message?.content);
      if (!text) break;   // 空文字（可能只是纯工具调用的消息）不产生 part
      if (parts.length === 0) { startSeq = e.seq; startTime = e.time; }  // 首个 part 决定气泡起始
      parts.push({ kind: 'text', seq: e.seq, step, text });
      break;
    }

    case 'tool/call': {
      if (parts.length === 0) { startSeq = e.seq; startTime = e.time; }
      parts.push({ kind: 'tool-call', seq: e.seq, step, name: d?.name, args: d?.arguments });
      break;
    }

    case 'tool/result': {
      if (parts.length === 0) { startSeq = e.seq; startTime = e.time; }
      parts.push({ kind: 'tool-result', seq: e.seq, step, text: textOf(d?.message?.content), isError: d?.error != null });
      break;
    }

    case 'system/message': {
      // 系统提示词（source.kind === 'system-prompt'）是内部内容，不显示
      if (d?.message?.source?.kind === 'system-prompt') break;
      const text = textOf(d?.message?.content);
      if (!text) break;
      if (parts.length === 0) { startSeq = e.seq; startTime = e.time; }
      parts.push({ kind: 'system', seq: e.seq, step, text });
      break;
    }

    default:
      break;   // step/start、step/end、request/*、approval/*、内部事件 → 忽略
  }
}

flush();   // 收尾：把最后一个还没落的 AI 回复发出去
return bubbles;
```

### 各事件如何聚合成气泡和 part

**`turn/start` → `turn/end`（轮次边界）**

- `turn/start`：记录 `currentTurn`，并 `flush()` 上一轮的 AI 回复。
- `turn/end`：`flush()` 本轮 AI 回复，清空 `currentTurn`。
- 轮次是"用户一问 + AI 一答"的边界，用来给气泡标 `turn` 序号、并决定 AI 气泡何时收口。

**`user/message`（用户消息）**

- **过滤**：DSH 会注入多条 `role=user` 的内部消息（如 agent-instructions 指令、runtime-context 上下文、skill-catalog 技能目录），只有 `source.kind === 'user'` 才是用户真正输入的，其余 `break` 丢弃。
- **先 flush 再 push**：用户消息意味着上一轮 AI 回复结束，所以先 `flush()` 把攒着的 AI parts 落成气泡，再 push 用户气泡。

**`assistant/message` + `tool/call` + `tool/result` + `system/message`（AI 气泡的 parts）**

这四类都往 `parts` 缓冲区里 push，最终由 `flush` 合并成**一个** AI 气泡：

| 事件 | part.kind | 数据来源 | 说明 |
| --- | --- | --- | --- |
| `assistant/message` | `text` | `d.message.content` 里的 text 块 | 空文字跳过（纯工具调用不产生文字 part） |
| `tool/call` | `tool-call` | `d.name` + `d.arguments` | 工具调用（函数名 + 参数 JSON 字符串） |
| `tool/result` | `tool-result` | `d.message.content` | `isError` 由 `d.error != null` 判断 |
| `system/message` | `system` | `d.message.content` | 过滤掉 `system-prompt`（系统提示词是内部内容不显示） |

- 每个 part 记录自己的 `seq` 和 `step`（多步 agent 时区分步骤）。
- `startSeq`/`startTime` 由**首个 part** 决定（气泡的起始 = parts 里第一条的 seq/time）。

**`default`（忽略其余事件）**

`step/start`、`step/end`、`request/*`、`approval/*`、各种内部事件都走 `default: break`，不产生气泡。这是"只挑对聊天界面有意义的事件"的思路。

### `textOf`（内容提取）

```ts
function textOf(content: unknown): string {
  if (!Array.isArray(content)) return '';
  return content
    .filter((b: any) => b?.type === 'text' && typeof b.text === 'string')
    .map((b: any) => b.text)
    .join('');
}
```

`content` 是 `ContentBlock[]`，可能含 `text` / `image` / `tool-call` 等块，这里**只取 `text` 块拼接**（图片/工具调用块在文字场景下忽略）。

> 小结：`toBubbles` 本质是一个**状态机**——用 `parts` 缓冲区和 `currentTurn` 游标，把"扁平的事件流"折叠成"轮次明确、气泡分层的聊天结构"，供 `chat.vue` 直接渲染。它和 B.5 的 `bubbleText()`（渲染时只取 `text` part）配合，完成了"事件 → 数据 → 视图"的最后一公里。

## 常见坑速查（App 端）

1. **WebSocket 带不上 Cookie**：App 端原生 WebSocket 不认 `connectSocket` 的 `header.Cookie`，必须写系统 CookieManager（A.3 / A.10 / B.1）。
2. **header 拼错**：`uni.request` 用 `header`（单数），不是 `headers`（A.2）。
3. **无参 RPC 方法不能带 request**：`session/modelCatalog`、`agentPresets/list` 的 args 必须是空对象，否则 Typert 拒绝（B.3）。
4. **`onReady` 之前量不到尺寸**：`uni.createSelectorQuery` 要在 `onReady` 里调用（A.13）。
5. **query 参数透传到 DOM**：uni-app 会把页面 query 参数当 attribute 透传，`defineOptions({ inheritAttrs: false })` 关掉（A.12）。
6. **`navigateTo` 最多 10 层**：无限下钻场景注意栈深度，或改用 `redirectTo`（A.5）。
7. **WebSocket 断线无重连**：当前 `onClose` 只提示，生产环境需加退避重连（B.4）。
