# 知识面缺失分析

> 这是根据项目联调过程中「你实际问过的问题」反推出来的知识缺口清单，按影响大小排序。
> 每个缺口都标了「项目里哪里用到」，方便对照源码补课。

---

## 域一：网络协议与安全（最核心，坑最多）

### 1. HTTP 安全头 ≠ 身份凭证

- **原问**：「是不是 APP 给桥的请求里带了很多证明身份的信息…被拒…App 不能改？」
- **缺口**：把 `Origin` / `Sec-Fetch-*` / `Referer`（**来源标记**）和 `Cookie`（**身份凭证**）当成一回事。它们是两套东西：一个回答「你从哪来」，一个回答「你是谁」。
- **项目里用到**：DSH 防火墙先查「来源标记」再查「身份」，App 控制不了来源标记，只能靠桥剥掉（`bridge.js` 转发时删 `origin`/`sec-fetch-*`/`referer`）。
- **补什么**：搜「浏览器 Origin vs Cookie」「Fetch Metadata Request Headers」「同源策略」。

### 2. HTTPS/TLS 加密在哪一层

- **原问**：「https 和 http 有什么差异，代码要改吗？」
- **缺口**：以为用 https 就得在桥/DSH 配证书。实际 TLS 只在「App ↔ Cloudflare」这一段，Cloudflare 解密后**明文**转发给本机桥，桥从头到尾不碰 TLS。
- **项目里用到**：`bridge.js` 只写明文 HTTP；`cloudflared` 负责加密。
- **补什么**：搜「TLS 终止（TLS termination）」「反向代理」。

### 3. HTTP 重定向 + Cookie 传递

- **缺口**：为什么 plus.net 自动跟随 303 后 `Set-Cookie` 就「丢了」——303 响应和最终 200 是两个不同响应，cookie 只在 303 上，plus.net 只把最终 200 暴露给你。
- **项目里用到**：stage 1「未拿到 cookie」的根因，也是必须引入桥用 Node http（不自动跟随）抓 303 的原因。
- **补什么**：搜「HTTP 3xx 重定向」「Set-Cookie 属性（HttpOnly、SameSite）」。

## 域二：进程与模块系统（start.mjs 暴露最多）

### 4. 进程树 / 孤儿进程

- **原问**：「窗口退出没关 DSH web，检查关闭逻辑」——你的判断是对的。
- **缺口**：`child.kill()` 只杀 cmd.exe 一层，Electron 孙进程成孤儿继续占 3080，需要 `taskkill /T` 杀整棵树。
- **项目里用到**：`start.mjs` 的 `killAll()` 就是修这个 bug。
- **补什么**：搜「Windows 进程树」「孤儿进程」「taskkill /T」。

### 5. ES Module vs CommonJS

- **原问**：「`__dirname` 不是声明的变量吗？」
- **缺口**：`.js`（CommonJS）里 `__dirname` 是 Node 白送的内置变量；`.mjs`（ESM）里没有，要自己 `const` 算出来。
- **项目里用到**：`start.mjs`（.mjs + import）与 `bridge.js`（.js + require）两套模块系统并存。
- **补什么**：搜「ESM vs CommonJS」「import.meta.url」「__dirname in ESM」。

### 6. 子进程 stdout/stderr 管道捕获

- **原问**：「token 能不能从管道抓到」「dsh web 不是本来就是控制台吗」。
- **缺口**：Electron 在 `ELECTRON_RUN_AS_NODE=1` 下就是纯 Node 进程，`console.log` 走标准 stdout，能被 `spawn` + `stdio:'pipe'` 捕获。
- **项目里用到**：`start.mjs` 抓 token（stdout）和隧道 URL（stderr）。
- **补什么**：搜「Node child_process spawn」「stdout vs stderr」。
