# DSH 移动端审批功能设计方案

> 状态：设计稿，供审核，**尚未写代码**。
> 目标：DSH 的 agent 执行需要审批的工具（运行 shell 命令、写文件等）时，App 弹出审批卡片，用户允许/拒绝后回传，agent 继续或中止。

---

## 一、现状与要解决的问题

- DSH 桌面 GUI 在 agent 要执行敏感工具时会弹审批卡片。
- 当前移动 App **完全看不到这个过程**：`chat.vue` 的 `bubbleText()` 用 `filter(p => p.kind === 'text')` 把 `tool-call` / `tool-result` / `system` 全部过滤掉了，审批事件更是被 `history.ts` 的 `default` 分支直接忽略（源码注释里就写着 `approval/*` 被忽略）。
- 本方案补齐：**agent 要动手 → App 弹审批 → 用户允许/拒绝 → 结果回传 → agent 继续或中止**。

---

## 二、协议事实（已从 DSH 源码确认）

审批相关的三个事件都走 `session/follow` 流（`SessionEventMap`）：

| 事件 | 载荷 | 含义 |
|---|---|---|
| `approval/asked` | `{ id: ApprovalRequestId; toolName: string; callId?: ToolCallId; reason?: string }` | agent 请求审批某个工具 |
| `approval/decided` | `{ id: ApprovalRequestId; outcome: ApprovalOutcome }` | 审批已有结果 |
| `approval/policy` | `{ policy: ApprovalPolicy; source?: 'delegation' }` | 审批策略发生变化 |

审批结果枚举 `ApprovalOutcome`（源码确认）：

```ts
'allowed-once'  // 允许这一次
'rejected'      // 拒绝
'cancelled'     // 已取消
'unavailable'   // 工具本身无审批能力
```

Host 侧有 `approval/request` hook：`ctx.on("approval/request", (request, next) => ...)`，`next` 回调负责 resolve 结果。ACP 适配器（`dsh-acp`）通过 `client.session.requestPermission`（选项 `allow-once` / `reject-once`，最终映射回 `allowed-once` / `rejected`）转发给 ACP 客户端——这证实了「允许一次 / 拒绝」两种语义。

## 三、关键待确认点（实现前必须钉死）

审批「决定」的回传通道：**App 用的是 Remote API（HTTP + mux WebSocket），不是 ACP**。所以实现前需要在源码里确认 Remote API 暴露审批决定的具体方法 / 帧格式。候选：

- `session/control` 流的反向（client→server）帧；
- 或某个专门的审批 RPC 方法。

> ⚠️ 这一条不确认清楚，**不写回传代码**。否则很容易走错协议，浪费一次联调。

## 四、UI 设计

### 4.1 审批卡片（聊天流内联，不弹窗）

与桌面 GUI 一致，审批请求以**卡片形式插入消息流**，位置在对应的 `tool/call` 处（审批是 `tool/call` 与 `tool/result` 之间的一环）：

```
┌──────────────────────────────────┐
│ ⚠️ 需要你审批                      │
│ 工具：run_shell_command            │
│ 参数：{"command": "rm -rf build"}  │
│ 理由：清理构建缓存                   │
│         [允许一次]   [拒绝]         │
└──────────────────────────────────┘
```

卡片状态流转：`等待中`（黄）→ `已允许`（绿）/ `已拒绝`（红）/ `已取消`（灰）。

### 4.2 数据流

```
follow 流收到 approval/asked
  → bubbles 插入「待审批」卡片（记录 id + toolName + callId + reason）
用户点「允许 / 拒绝」
  → 调审批决定 RPC（传 id + outcome）
  → 本地乐观更新卡片为「已允许 / 已拒绝」
follow 流收到 approval/decided
  → 用服务端 outcome 校正卡片最终状态
  → 若 allowed-once，后续 tool/result 正常展示
```

## 五、实现步骤

1. **确认回传 RPC**（读源码，不确认不动手）。

4. `client.ts` 加审批决定方法（走确认后的 RPC）。
5. 与「工具调用展示」合并做：先展示 `tool/call`，在需要审批处插入审批卡片，审批通过后展示 `tool/result`。

## 六、与其它功能的耦合

- **强依赖「工具调用展示」**：审批卡片是工具调用的一部分。建议两者一起做，或先做工具展示、再加审批。
- **依赖断线重连**：审批期间断线会让审批请求「悬空」。重连后需靠 `approval/decided` 或重新拉历史来校正卡片状态。
- **依赖人设配置**：审批策略（哪些工具要审批）由 DSH 人设/权限配置决定，App 只负责呈现与回传，不决定「要不要审批」。

---

## 七、边界与建议

- 只做「允许一次 / 拒绝」两种动作，对应 `allowed-once` / `rejected`；`cancelled` / `unavailable` 作为只读状态展示，不提供操作。
- 暂不支持「总是允许」/「记住策略」这类持久化策略（属于 DSH 侧配置，超出移动端职责）。
