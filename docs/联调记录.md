# DSH 移动端联调排查记录（详细版）

> 目标：用 uni-app（H5 + Android App）远程控制本地 DSH 桌面应用（HTTP + WebSocket）。
> 本文以「DSH 插件 App」的视角，记录每一步：**请求经过哪些组件、DSH 实际返回了什么、App 读到什么、在哪个环节报错、报的是什么错、怎么定位的**。

---

## 〇、先分清几个工具分别是谁的

| 名字 | 是谁提供的 | 说明 |
|---|---|---|
| `uni.request` | uni-app（DCloud） | 跨端统一网络请求 API。**你 App 代码里调的就是它**。它只是壳，底层按端转发：H5 端走浏览器 XHR，App 端走 `plus.net.XMLHttpRequest`，小程序端走 `wx.request`。 |
| `uni.connectSocket` | uni-app（DCloud） | 跨端统一 WebSocket API。App 端底层走的是原生 `uni-webSocket` 插件（**不是** plus.net，是另一个原生实现）。 |
| `plus.net.XMLHttpRequest` | HTML5+（5+App）运行时 | App 端的**原生跨域 XHR**。`uni.request` 在 App 端底层就是调它。它是原生实现，不受浏览器同源限制，也**绕过了 Android 明文限制**（这点很关键）。 |
| `plus` / `plus.net` | HTML5+（5+App）运行时 | `plus` 是 DCloud 的 5+App 运行时**注入到 App 页面里的全局对象**（只在 App 端存在，H5 端没有）。`plus.net` 是它的「网络模块」，里面有 `XMLHttpRequest` 等。 |
| bridge.js | 你自己 | 跑在 DSH 同一台电脑上的 Node 脚本（反向代理 + 换 cookie）。 |
| cloudflared | Cloudflare | 隧道工具，把本机端口暴露成 `https://xxx.trycloudflare.com`。 |
| DSH | 你的桌面应用 | `dsh web` 起的 web 服务，提供浏览器 UI + HTTP/WS 接口。 |

**一条请求的完整链路（App 端）**：

```
你的 App 代码
  → uni.request / uni.connectSocket（uni-app 跨端壳）
  → plus.net.XMLHttpRequest / 原生 uni-webSocket 插件（5+App 原生实现）
  → 网络
  → DSH（或桥）
```

## 一、DSH 的 4 层安全机制（排查前先搞清）

1. **token 换 cookie**：`GET /?token=xxx` 校验通过 → 返回 **303 重定向 + Set-Cookie**（cookie 只在 303 上，不在最终页面）。
2. **cookie 按 Host 签名**：cookie 名 = `dsh-auth-<base64url(sha256(Host))>`，值 = `v1.<base64url(载荷)>.<base64url(签名)>`，载荷含 `authority`（= Host）、签发/过期时间。cookie 只对签发时那个 Host 有效。
3. **Host/Origin 防火墙**（`isTrustedApiRequest`）：`/api` 请求的 Host 必须是 loopback 或配置声明的受信任 host，否则 **403 "forbidden"**；还检查 `origin`、`sec-fetch-site` 等跨站标记。
4. **流式走 WebSocket**：`/api/remote.mux`，一个物理 WebSocket 复用多条逻辑流（`session/follow`）。

## 二、阶段 1：App 连不上（cookie 拿不到）

> 初始状态：App 刚建好，第一次尝试连接。App 代码里 `connect()` 用 `uni.request` 直连 DSH 做 token 交换（`GET http://192.168.8.219:3080/?token=xxx`），期望从响应头里读到 `Set-Cookie` 存下来。这一步就撞上了下面的问题。

### 2.1 现象（App 上看到）
点「连接」，提示 **「未拿到 cookie，token 可能无效」**。H5 端正常。

### 2.2 尝试 A：用 `uni.request` 读 Set-Cookie

- **链路**：App 代码 `connect()` → `uni.request`（底层 `plus.net.XMLHttpRequest`）→ 网络 → DSH 的 `authorizeIndex`。
- **实际发生了什么**：
  1. App 发起 `GET http://192.168.8.219:3080/?token=xxx`。
  2. DSH 返回 **`303 See Other`**，响应头带 `Set-Cookie: dsh-auth-xxx=v1.xxx` 和 `Location: ./`。
  3. `plus.net.XMLHttpRequest` 看到 303，**自动跟随重定向**，发起第二次请求 `GET /`。
  4. DSH 第二次返回 **`200 OK`**（index 页面），**这个响应上没有 Set-Cookie**。
- **报错在哪个环节、报的是什么**：App 代码读的是 `result.header['Set-Cookie']`，而 `result` 是**第二次 200 响应**，它的头里没有 Set-Cookie → 读到空 → 代码判定失败，弹「未拿到 cookie」。
- **推测**：`plus.net.XMLHttpRequest` 自动跟随 303，App 代码只能看到最终 200，看不到中间 303 上的 Set-Cookie。

### 2.3 尝试 B：`plus.net.XMLHttpRequest` + `followRedirects=false`

- **链路**：App 代码直接 `new plus.net.XMLHttpRequest()`，设 `followRedirects = false`，期望它不跟随 303、直接读 303 的 Set-Cookie。
- **实际返回**：第一次 `xhr.status === 0`，后续测试 `xhr.status === 200`（都读不到 Set-Cookie）。
- **报错环节**：`xhr.status` 不是 303；`readSetCookie(xhr)` 仍为空。
- **推测**：`followRedirects` 这个属性在 plus.net 运行时里**不存在/不生效**（类型声明里都没有它），XHR 还是自动跟随了 303，Set-Cookie 依然读不到。

### 2.4 尝试 C：赌 plus.net 有持久 cookie jar

- **链路**：App 代码 → `uni.request`（plus.net）→ DSH。不手动抓 cookie，赌 plus.net 会把 token 交换时拿到的 Set-Cookie 自动带到后续请求。
- **实际返回**：token 交换返回 200；但紧接着 `session/list` 返回 **401** → App 提示「token 无效或鉴权失败」。
- **报错环节**：`session/list` 的 401（DSH 判定没带有效 cookie）。
- **推测**：plus.net **不跨请求持久化 cookie**（token 交换的 Set-Cookie 只在那一次重定向链内有效，没存下来给下一个独立请求用）。

### 2.5 最终方案：引入「桥」
- **关键点**：**Node 的 http 模块不自动跟随重定向**，能直接读到 303 的 Set-Cookie。
- 桥提供 `/auth?token=xxx`：用 Node http 请求 DSH `/?token=xxx`，抓到 303 的 Set-Cookie，返回 `{ ok, cookie }` 给 App。

**结论**：阶段 1 解决，App 能拿到 cookie 了。

## 三、阶段 2：局域网下 WebSocket 连不上

> 前置动作：阶段 1 的「桥」落地后，App 改用桥换 cookie（`GET /auth?token=xxx`），拿到 cookie 后 `session/list` 通、能列出会话了。此时**点开一个会话** → 触发 `session/follow` 的 WebSocket，才暴露出下面的新问题。

### 3.1 现象
连接成功（`session/list` 有会话数），但选会话后提示「连接已断开」（列表走 HTTP，流式走 WebSocket）。

### 3.2 怎么验证
给 ws.ts 加日志，看 WebSocket 走到哪一步。

- **链路**：App 代码 `followSession` → `uni.connectSocket`（底层原生 uni-webSocket 插件，**不是** plus.net）→ 网络 → DSH `/api/remote.mux`。
- **实际返回**：
  ```
  [ws] url: ws://192.168.8.219:3080/api/remote.mux | cookie: 有
  [ws] onError        ← 没有 onOpen，握手直接失败
  ```
- **报错环节**：原生 WebSocket 插件报 `onError`（握手失败，连 onOpen 都没有）。

#### 复盘：onError 是「泛化错误」，这一步本该先看服务端

- `uni.connectSocket` 的 `onError` 回调**不携带任何信息**（没有状态码、错误码、reason、message），只表示「出错了」。
- 所以单看 App 侧日志，无法区分 `onError` 是下面哪一种：
  - `ws://` 明文被 Android 拦（客户端侧，请求根本没发出）
  - 网络不通（客户端侧）
  - 握手被 DSH 拒 401（cookie 没带对）
  - 握手被 DSH 拒 403（Host/Origin 防火墙）
- **正确的诊断顺序**：触发 WebSocket 的同时，看 DSH 的 `dsh web` 终端有没有日志——
  - 终端没反应 → WebSocket 根本没到达 DSH → 客户端侧问题（明文/网络）
  - 终端显示 401 → cookie 问题
  - 终端显示 403 → Host/Origin 防火墙
- 这一步当时被跳过了，直接从「onError」跳到了「可能 cookie 没带」，多绕了一圈。

### 3.3 尝试：把 cookie 写进系统 CookieManager
- **方案**：`plus.android` 调 `android.webkit.CookieManager`，把 cookie 写进系统 cookie 库，想让原生 WebSocket 自动带上。
- **实际返回**：
  ```
  [cookie] 已写入 CookieManager: dsh-auth-8TuQrL7o...
  [cookie] 读回: dsh-auth-8TuQrL7o...=v1.eyJ...authority:"192.168.8.219:3080"...
  ```
  写进去、读回来都正常，**但 WebSocket 仍 onError**。
- **推测（❌ 后来证实是错误的）**：当时归因于「`ws://` 明文被 Android 原生 WebSocket 拦——HTTP 走 plus.net 原生栈绕过明文限制、WebSocket 受限制」。这个推测**从未被证实**，且逻辑有漏洞：若 Android 全局拦明文，`http://` 也该被拦，但它是通的；要圆这个结论必须再假设「plus.net 绕过、uni-webSocket 不绕过」，这层假设也没验证。**真正的原因后移到了阶段 4 的 `origin`/`sec-fetch` → DSH 403**（桥剥掉这些头后才通）；而桥（Node.js）连 DSH 的 `ws://` 明文一直是通的，反证「明文」从来不是问题。
- **为什么试 CookieManager（有依据的部分）**：App 端有两条独立的 cookie 路径——`uni.request`（plus.net）认手动 `header.Cookie`（session/list 已验证生效），而 `uni.connectSocket`（原生 uni-webSocket 插件）是另一套原生实现，可能不认手动 header、只读系统 CookieManager。所以这个尝试是在测「原生 WebSocket 是不是走 CookieManager 这条路」，结果（读回正常仍 onError）确实排除了 cookie 路径。
- **草率的部分**：顺序反了。本该先看 DSH 终端日志确认「有没有到达 + 回 401 还是 403」，再定向查；而不是从泛化错误直接赌一个假设。

### 3.4 思路转向
> 注：当时改走 HTTPS 隧道的理由是「`ws://` 明文被拦」，这个理由后来被证明是错的（真正原因是阶段 4 的 origin/sec-fetch → 403）。但「走隧道」对后面的「不在局域网远程演示」仍是必要方向，没白走。

改用 **cloudflared HTTPS 隧道**，让 App 走 `https` / `wss`。

## 四、阶段 3：隧道下 HTTP 返回 403 forbidden

> 前置动作：从「局域网直连」切换成「走 cloudflared 隧道」。具体改了这些——

1. 新开两条 cloudflared 隧道：
   - DSH 隧道 A（转发 3080）→ `https://dispatch-slip-sometimes-parade.trycloudflare.com`
   - 桥隧道 B（转发 3081）→ `https://workers-background-pocket-previews.trycloudflare.com`
2. App「登录 url」：`http://192.168.8.219:3080`（局域网）→ `https://dispatch-slip-sometimes-parade.trycloudflare.com`（DSH 隧道 A）
3. App「桥 url」：`http://192.168.8.219:3081`（局域网）→ `https://workers-background-pocket-previews.trycloudflare.com`（桥隧道 B）

于是 `session/list` 的请求链路从「局域网直连」变成了「走 DSH 隧道」：

- 之前：App → `http://192.168.8.219:3080/api/session/list` → DSH（DSH 看到 Host = `192.168.8.219:3080`）
- 现在：App → `https://dispatch-slip-sometimes-parade.trycloudflare.com/api/session/list` → cloudflared（DSH 隧道 A）→ DSH（DSH 看到 Host = `dispatch-slip-sometimes-parade.trycloudflare.com`）

（注：这一步里桥只负责「换 cookie」，`session/list` 走的是 DSH 隧道 A，不经过桥。）

### 4.1 现象 + 返回
```
[send] session/list HTTP 403 | body: "forbidden"
```

### 4.2 怎么定位
- **链路**：App 代码 → `uni.request`（plus.net）→ 网络 → cloudflared（DSH 隧道 A）→ DSH。
- **DSH 看到了什么**：cloudflared 保留原始 Host，所以 DSH 看到的 Host 是 `xxx.trycloudflare.com`。
- 读源码 `isTrustedApiRequest`：确认 403 来自 **Host 白名单**（`if (!isTrustedApiRequest(...)) return 403`）。
- **报错环节**：DSH 的防火墙，因为 `xxx.trycloudflare.com` 不在白名单（只有 `192.168.8.219` 和 loopback）→ 403。

### 4.3 尝试 A：桥伪装 Host = 隧道地址
- 方案：`node bridge.js dispatch-slip-....trycloudflare.com`，让桥用隧道 host 去签名 cookie。
- 返回：App **401**。
- 推测：cloudflared 把 Host 改写回源站 `192.168.8.219:3080`，cookie 的 authority（隧道 host）对不上。

### 4.4 尝试 B：桥用局域网地址签 cookie
- 返回：仍 **401**。
- 矛盾：两种 Host 都不行，说明「对齐 Host」这条路有问题。

### 4.5 关键诊断
- 返回：
  ```
  [cookie] 读回: dsh-auth-ycP7...（authority: dispatch-slip...trycloudflare.com）;
                 dsh-auth-8TuQr...（authority: 192.168.8.219:3080）
  ```
  系统 CookieManager 里同时有**两个 authority 的 cookie**；且 `session/list` 是 **403 "forbidden"（不是 401）**。
- 结论：403 是 **Host 白名单**问题，不是鉴权问题。隧道 host 根本不在白名单，而隧道地址每次重启都变——**走隧道 + 白名单写死，天生矛盾**。

## 五、阶段 4：桥反向代理 + 最后的 WebSocket origin 检查

> 前置动作：把桥从「只换 cookie」改造成「反向代理」，App 的连接目标也变了——
>
> 1. bridge.js：从「只提供 /auth」改成「/auth + /api 转发 + WebSocket 转发」，并且转发时把 Host 改写成白名单地址、剥掉 origin/sec-fetch。
> 2. App「登录 url」：DSH 隧道 A（`https://dispatch-slip-....trycloudflare.com`）→ 桥隧道 B（`https://workers-background-....trycloudflare.com`），因为现在 API 也走桥了。
> 3. DSH 隧道 A（转发 3080 那条）关掉，不再需要。
>
> 于是 App 只连桥这一条隧道，桥负责「改 Host + 剥跨站头 + 透传 cookie」。

### 5.1 思路
放弃「对齐 Host」，改为：**桥跑在 DSH 同一台机器上，桥连 DSH 用白名单里的 `192.168.8.219:3080`，把 Host 改回去**；App 只连「桥隧道」一条隧道。

- 结果：HTTP 通了（`session/list` 返回 200）。

### 5.2 又哪里不通
HTTP 通了，但**选会话后 WebSocket 仍断**。

### 5.3 怎么验证 + 返回
给桥加 WebSocket 每步日志：
```
[bridge] ws upgrade: /api/remote.mux | cookie: 有   ← 桥收到升级请求
[bridge] ws target 已连接                            ← 桥连上 DSH
[bridge] ws target 关闭                              ← DSH 主动关闭
[bridge] ws client 关闭                              ← App 侧跟着关
```
- **报错环节**：DSH 主动关闭连接（拒绝了这次 WebSocket）。

### 5.4 怎么定位
读源码 `dsh-api-gateway/lib/index.js`：
```js
const admission = webCtx.connection.admit(req);
if ('rejection' in admission) rejectRemoteStreamUpgrade(socket, admission.rejection);
```
确认 **WebSocket 升级和 HTTP 走的是同一个 `connection.admit`**，除了 Host 白名单和 cookie，还检查：
- `sec-fetch-site === "cross-site"` → 拒绝
- `origin` 头（若有）必须和 Host 一致，否则拒绝

App 原生 WebSocket 带了一个本地 `origin`，跟 `192.168.8.219:3080` 对不上 → DSH 403。

### 5.5 修复
桥转发时**剥掉 `origin` / `sec-fetch-*` / `referer`**，只透传 Cookie，Host 改写成白名单地址。剥掉后 `origin === undefined`，防火墙直接放行。

- 返回：**连接成功，流式回复正常** ✅

## 六、最终架构

```
手机 App
  │  https / wss（只连这一条 cloudflared 隧道 B）
  ▼
cloudflared（桥隧道，转发到本机 3081）
  ▼
bridge.js（本机 3081，反向代理）
  │  转发时做三件事：
  │   1. Host 改写成 192.168.8.219:3080（过白名单）
  │   2. 剥掉 origin / sec-fetch-* / referer（过跨站检查）
  │   3. 透传 Cookie（过鉴权）
  ▼
DSH（本机 192.168.8.219:3080）
```

## 七、Cookie 是怎么交换的

1. App 请求桥：`GET /auth?token=xxx`。
2. 桥用 Node http 请求 DSH：`GET /?token=xxx`，Host 设为 `192.168.8.219:3080`。
3. DSH 校验 token 有效 → 返回 **303 + Set-Cookie**：
   - 名 = `dsh-auth-<base64url(sha256("192.168.8.219:3080"))>`
   - 值 = `v1.<base64url(载荷)>.<base64url(签名)>`，载荷含 `authority`、签发/过期时间
   - 属性：`Max-Age`、`Path=/`、`HttpOnly`、`SameSite=Strict`
4. Node http 不跟随重定向，桥读到 Set-Cookie，取 `name=value` 部分。
5. 桥返回 `{ ok, cookie }` 给 App。
6. App 存下 cookie（本地 key + 系统 CookieManager）。
7. 后续 HTTP / WebSocket，App 手动带 `Cookie: name=value`，桥透传给 DSH。

## 八、WebSocket 是怎么交换的

1. App `uni.connectSocket` 连 `wss://桥隧道/api/remote.mux`，带 `Cookie` 头。
2. cloudflared 解密后转发到桥（3081）。
3. 桥 HTTP 服务收到 `Upgrade: websocket`，用 `net.connect` 连本机 DSH 的 3080，原样转发 Upgrade 请求（Host 改写、剥 origin/sec-fetch、透传 Cookie）。
4. DSH 校验通过 → 返回 `101 Switching Protocols`。
5. 桥用双向管道 `socket.pipe` 原样转发后续字节，形成透明通道。
6. App 与 DSH 在通道上交换 mux 帧（open / item / end），实现流式。

## 九、各安全策略归属表

| 安全策略 | 是谁的 | 内容 | 怎么解决的 |
|---|---|---|---|
| token 换 cookie（303 + Set-Cookie） | DSH 浏览器鉴权 | 303 下发签名 cookie，按 Host 绑定 | 桥用 Node http 抓到 Set-Cookie |
| Host 白名单（403 forbidden） | DSH `isTrustedApiRequest` | `/api` 只接受 loopback 或受信任 host | 桥把 Host 改写成 `192.168.8.219:3080` |
| origin / sec-fetch 检查（403） | DSH `isTrustedApiRequest` | 跨站防护：origin 须与 Host 一致 | 桥剥掉 origin / sec-fetch-* / referer |
| ~~明文 http/ws 限制~~（❌ 误判，未证实） | ~~Android~~ | 当时推测 ws 被明文拦，但逻辑不成立（http 也明文却通），从未证实 | 真正原因是上一行的 origin/sec-fetch 403 |
| 自动跟随 303 丢 Set-Cookie | App 网络库（plus.net） | 跟随重定向只暴露最终响应 | 桥代抓 cookie |

## 十、一句话总结

H5 能直接连，是因为浏览器自动处理了「重定向 + cookie jar + 同源」。App 端这三样都没有，所以：先用桥解决「抓 cookie」，再用「桥反向代理 + 改 Host + 剥跨站头」解决 DSH 的 Host 白名单、跨站检查；「走隧道（wss）」则是为了不在局域网也能远程访问，不是解决明文（明文从未被证实是问题）。
